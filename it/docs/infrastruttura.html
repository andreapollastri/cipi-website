Infrastruttura

cipi php

PHP 8.5 è preinstallato durante il setup. Puoi aggiungere altre versioni in qualsiasi momento; da v4.5.12 Cipi analizza le sorgenti APT per codename Ubuntu — di solito la PPA ondrej/php su 24.04, packages.sury.org su 26.04 quando Launchpad non ha una suite, oppure Ubuntu main come ultima risorsa (co-installabili 8.3–8.5 dove il repository scelto le supporta).

Da v4.5.4 Cipi include Deployer 8, che richiede PHP ≥ 8.3. cipi php install, cipi php switch, cipi app create e cipi app edit accettano quindi solo 8.3, 8.4 e 8.5. Le versioni legacy (7.4–8.2) restano rilevabili e rimovibili, così puoi ancora ripulire un server pre-4.5.4 con cipi php remove <old-version>.
bash
$ cipi php list              # list installed versions, status, and system default
$ cipi php install 8.4       # install an additional PHP version (8.3–8.5)
$ cipi php switch 8.4        # set system default (root/cipi, API pool)
$ cipi php remove 8.1        # remove a version, incl. legacy (blocks if default or apps use it)
$ cipi php upgrade           # apply security patches to all installed PHP packages

Aggiornamenti di sicurezza

Da v4.7.13, i pacchetti PHP sono esclusi da unattended-upgrades e gestiti da Cipi. cipi php upgrade esegue apt-get update e --only-upgrade su ogni pacchetto php* e libphp* installato, poi riavvia i pool PHP-FPM interessati. Quando SMTP è configurato e i pacchetti sono stati aggiornati, Cipi invia un'email (trigger php_upgrade; disabilita con cipi notifications disable php_upgrade).

Un controllo settimanale parte automaticamente la domenica alle 03:30 tramite crontab di root (wrappato da cipi-cron-notify). Log: /var/log/cipi/php-upgrade.log. I server esistenti ricevono il cron con cipi self-update (migrazione 4.7.13).

PHP predefinito di sistema vs PHP specifico per app

Il default di sistema è la versione PHP usata dagli utenti root e cipi, dal pool FPM dell'API Cipi, del pool FPM GUI (se installato) e dal queue worker dell'API. Usa cipi php switch <ver> per cambiarla. Il comando migra il pool API (e il pool FPM GUI se installato), ricrea i socket del pannello e riavvia il worker API. Da 5.0.9+, PUT /api/php/default avvolge questa operazione via panel API (ability php-manage). Da 5.0.10–5.0.12, switch tollera successo parziale di update-alternatives, rimonta root read-only quando serve e mantiene i pool FPM API/GUI sulla versione target per evitare nginx 502.

REST: GET /api/php, POST /api/php/install, DELETE /api/php/{version}, PUT /api/php/default (API 1.15.0+ / Cipi 5.0.6+). JSON CLI: cipi php list --json (da 5.0.6).

Ogni app ha la propria versione PHP (impostata a app create o tramite cipi app edit --php=). Deployer, Composer, i trigger di deploy nel crontab e cipi sync import girano sempre con il PHP configurato per l'app — mai con il default di sistema.

Per passare un'app esistente a una versione diversa:

bash
$ cipi app edit myapp --php=8.5

Cambia la versione PHP a caldo con zero downtime: aggiorna il pool FPM, il socket Nginx, i worker Supervisor, il crontab, la config Deployer e .env in un'unica operazione atomica.

cipi ini

Disponibile dalla v5.1.0. Un modo guidato per cambiare le impostazioni PHP senza cacciare il php.ini giusto. Ogni cambio server-wide raggiunge entrambi i SAPI — PHP-FPM e CLI — così quello che vedono le richieste web è anche quello che vedono queue worker, artisan e cron.

bash
$ cipi ini list                                # valori effettivi e quale layer li ha impostati
$ cipi ini list --app=shop                     # come li vede un'app
$ cipi ini get memory_limit                    # una sola impostazione
$ cipi ini set upload_max_filesize=50M         # server-wide (FPM + CLI)
$ cipi ini set memory_limit=512M --app=shop    # per una sola app
$ cipi ini unset memory_limit --app=shop       # torna al valore più ampio
$ cipi ini reset [--app=shop]                  # torna ai default Cipi
$ cipi ini keys                                # cosa si può impostare, e cosa no

Cosa fa per te

  • Alza le impostazioni che ti caperebbero in silenzio. Impostare upload_max_filesize alza anche post_max_size e memory_limit quando altrimenti lo limiterebbero, e client_max_body_size di Nginx viene segnalato quando lo farebbe.
  • Rifiuta ciò che non va impostato così. Le chiavi impostabili sono una whitelist esplicita — vedi cipi ini keys. open_basedir, auto_prepend_file, extension e compagnia vengono rifiutati per nome, con il motivo, perché Cipi li gestisce come parte dell'isolamento delle app.
  • Gli override per-app vincono. --app=<app> scrive nel pool FPM di quell'app, che batte il file server-wide — solo per quell'app.

Perché andava sistemato

Prima della 5.1.0 ogni pool FPM hardcodava upload_max_filesize, post_max_size e max_execution_time, e i valori del pool battono conf.d — quindi un cambio php.ini server-wide non raggiungeva nessuna app. Inoltre Cipi scriveva 99-cipi.ini solo per FPM, lasciando il SAPI CLI (queue worker, artisan, cron) sui default del pacchetto PHP.

Nella 5.1.0 i pool portano solo ciò che è genuinamente per-app (open_basedir, il log errori, gli override espliciti) e ereditano tutto il resto; entrambi i SAPI ricevono il loro file; e la migration 5.1.0 backfill del 99-cipi.ini CLI e riscrive i pool esistenti all'update.

Ogni cambio spara il trigger ini_set, così un'impostazione PHP non cambia mai su un server condiviso senza traccia. Un'app può anche portare versione PHP e impostazioni per-app nel repository — vedi cipi.yml.

cipi db

Cipi crea automaticamente un database dedicato per ogni app Laravel durante app create. MariaDB (porta 3306) è il default nativo; da v4.8.0 puoi anche installare PostgreSQL opzionale (porta 5432) e scegliere un engine per database o app. Le app custom non ricevono un database — usa cipi db create --name=<app> se ti serve (es. per WordPress o un altro CMS). Dopo il setup viene mostrato un URL di connessione pronto all'uso (MariaDB: mariadb+ssh://), che combina credenziali SSH, IP del server e informazioni sul database per client GUI come TablePlus, DBeaver o Sequel Pro.

Engine (v4.8.0+)

bash
$ cipi db install pgsql              # install optional PostgreSQL
$ cipi db uninstall pgsql|mariadb    # remove a non-default engine (destroys data)
$ cipi db default mariadb|pgsql      # server-wide default when --engine is omitted
$ cipi db engines                    # installed engines, ports, and default

Ciclo di vita del database

bash
$ cipi db create                              # interactive
$ cipi db create --name=analytics             # non-interactive (default engine)
$ cipi db create --name=analytics --engine=pgsql
$ cipi db list [--engine=mariadb|pgsql]       # list databases with sizes
$ cipi db backup myapp [--engine=…]
$ cipi db restore myapp backup.sql.gz [--engine=…]
$ cipi db password myapp [--engine=…]         # regenerate password
$ cipi db delete analytics [--engine=…]

Le app Laravel memorizzano l'engine scelto nei metadati dell'app; backup, sync e cipi app reset-db-password lo seguono. Usa cipi app create --engine=pgsql (o il prompt interattivo) per provisionare un'app Laravel su PostgreSQL — .env e l'URL di connessione corrispondono all'engine. Reset password root: cipi reset db-password [--engine=].

cipi alias

Aggiungi più domini o sottodomini a qualsiasi app. Dopo aver aggiunto alias, esegui cipi ssl install per provisionare o rinnovare il certificato con copertura SAN per tutti i domini. Da v4.8.0, cipi alias add|remove rigenera il vhost e riapplica SSL con certbot install --redirect così HTTPS non viene perso.

bash
$ cipi alias add myapp www.myapp.com
$ cipi alias add myapp myapp.it
$ cipi alias add myapp '*.myapp.com'   # wildcard (v5.1.0+) — quotarlo
$ cipi alias list myapp
$ cipi alias remove myapp myapp.it

Dalla v5.1.0 gli alias wildcard come *.example.com sono accettati — Nginx matcha nativamente un server_name wildcard, e le app multi-tenant ne hanno bisogno. Quota il pattern così la shell non lo espande, e emetti il certificato con cipi ssl install myapp --dns=cloudflare --wildcard: HTTP-01 non può validare un wildcard.

Per i redirect canonici www ↔ apex, preferisci cipi www invece di gestire a mano l'host counterpart.

cipi www

Disponibile da v4.8.0. Gestisci alias www/apex e redirect canonici 301 per un'app. Lo stato vive in apps.json (www_redirect); Nginx emette un server block dedicato al redirect (percorso ACME lasciato pubblico) che sopravvive alla rigenerazione del vhost. SSL viene riapplicato tramite certbot install --redirect.

bash
$ cipi www add myapp              # add counterpart host (www ↔ apex)
$ cipi www force-to-root myapp    # 301 www.domain → domain
$ cipi www force-from-root myapp  # 301 domain → www.domain
$ cipi www clear myapp            # clear redirect state
$ cipi www status myapp           # inspect redirect state

force-to-root / force-from-root aggiungono automaticamente l'alias mancante quando serve.

cipi domains

Disponibile da v4.5.5. Comando di top level che elenca ogni dominio e alias su tutte le app in un'unica tabella — la controparte globale di cipi alias list <app> per app. Ideale per auditare l'intera mappa dominio→app o individuare un dominio a cui manca ancora un certificato.

bash
$ cipi domains   # list all domains and aliases across every app

Ogni riga mostra le seguenti colonne:

Colonna Descrizione
DOMAIN Il nome del dominio o dell'alias. Le righe sono ordinate alfabeticamente per dominio.
APP L'app proprietaria del dominio.
KIND primary o alias.
TYPE Laravel o Custom.
PHP La versione PHP dell'app.
DOCROOT public per app Laravel, /<docroot> per app custom.
BRANCH Il branch Git deployato per l'app.
LAST DEPLOY Età relativa leggibile (just now, 10m ago, 2h ago, 3d ago, 2w ago, 2mo ago, 2y ago) — derivata dal mtime del symlink current dell'app, che Deployer riallinea atomicamente a ogni deploy riuscito. Mostra - quando l'app non è mai stata deployata.
SSL Stato del certificato per nome (✓/✗), rilevato da /etc/letsencrypt/live/<domain>.
REPOSITORY Il repository Git, oppure (SFTP only) per app custom senza repo.
(suffix) Quando l'app proprietaria è sospesa, ogni riga termina con ⏸ suspended (giallo). Il footer riporta anche quante app sono sospese.

Un footer riassume i totali — numero di domini, app, certificati e app sospese — così puoi auditare l'intera mappa a colpo d'occhio.

cipi ssl

Certbot gestisce i certificati Let's Encrypt. I certificati si rinnovano automaticamente tramite un cron settimanale. cipi ssl status mostra le date di scadenza con avvisi a colori: verde (>30 giorni), giallo (14–30 giorni), rosso (<14 giorni).

bash
$ cipi ssl install myapp   # provision / renew — includes all aliases (SAN)
$ cipi ssl force myapp     # re-apply HTTP→HTTPS redirect (no new issuance)
$ cipi ssl renew            # force renewal of all certificates
$ cipi ssl status           # show all certs with expiry dates

# DNS-01 via Cloudflare (v5.0+) — wildcard certs
$ cipi ssl dns set --provider=cloudflare --token=YOUR_CF_TOKEN
$ cipi ssl install myapp --dns=cloudflare
$ cipi ssl install myapp --dns=cloudflare --wildcard

Da v4.8.0, cipi ssl force <app> riapplica il redirect HTTP → HTTPS per un'app che ha già un certificato Let's Encrypt — senza emetterne uno nuovo. cipi ssl install imposta anche force_https in apps.json automaticamente.

Da v5.0, le challenge opzionali DNS-01 via Cloudflare sostituiscono il flusso HTTP-01 predefinito quando ti servono certificati wildcard o non puoi esporre la porta 80. Configura una volta con cipi ssl dns set, poi passa --dns=cloudflare (e opzionalmente --wildcard) a cipi ssl install.

Dopo aver aggiunto alias di dominio con cipi alias add, esegui sempre di nuovo cipi ssl install per provisionare un nuovo certificato SAN che copra tutti i domini. Se il redirect HTTPS è andato perso dopo un cambio vhost, usa cipi ssl force invece di riemettere.

cipi nginx default-server

Disponibile dalla v5.1.0. Rivendica quale tra :80 / :443 non ha un default server e chiude le richieste senza match con una risposta vuota (444).

bash
$ cipi nginx default-server status
$ cipi nginx default-server on
$ cipi nginx default-server off

Cipi ha sempre avuto un default server su :80, ma mai su :443. Una richiesta HTTPS con un Host sconosciuto cadeva quindi sul primo vhost che Nginx aveva caricato — per un'app multi-tenant con wildcard, dritto in un tenant resolver che non sa parsarla.

È abilitato sulle install fresh, e la migration 5.1.0 lo rivendica sui server esistenti dove nient'altro lo fa già. Se un altro vhost possiede legittimamente il default server, il comando lo dice e non cambia nulla.

cipi backup

Fai backup di file applicazione e database su disco locale, su Amazon S3, o su qualsiasi provider S3-compatibile (Cloudflare R2, Hetzner Object Storage, DigitalOcean Spaces, Backblaze B2, Scaleway, MinIO, …).

Dalla v5.1.0 i backup sono guidati da profili invece di un job notturno hardcoded. Un profilo risponde a quattro domande — cosa prende, quanto spesso gira, dove va e per quanto viene tenuto — e i profili sono indipendenti, così una copia database ogni 30 minuti sul disco sta tranquillamente accanto a una copia full cifrata notturna su S3.

Stai aggiornando da 5.0.x? La migration 5.1.0 converte il vecchio job notturno in un profilo chiamato default, portando la retention --weeks esistente, e prende in carico lo schedule con un blocco crontab gestito. Niente fuori da quel blocco viene toccato, e cipi backup prune <app> --weeks=N continua a fare prune del layout pre-5.1.

1 — Destinazioni

cipi backup configure salva le credenziali S3 condivise da ogni profilo. Dalla v5.1.0 puoi lasciare il bucket vuoto per backup solo-locali, che finiscono in /var/backups/cipi.

bash
$ cipi backup configure
# → AWS Access Key ID
# → AWS Secret Access Key
# → Bucket name        (lascia vuoto per backup solo-locali)
# → Region
# → Endpoint URL       (lascia vuoto per AWS; obbligatorio per altri provider)

$ cipi backup status                 # destinazioni, profili, ultima run, in ritardo

2 — Profili di backup

Crea un profilo una volta; poi gira da solo. Due tipici:

bash
# Ogni 30 minuti — solo database, tenuti sul server, ultime 48 run
$ cipi backup profile add hourly-db --scope=db \
      --databases='shop,tenant_*' --exclude-tables='*.jobs,*.telescope_*' \
      --every=30m --keep=48 --dest=local

# Ogni notte alle 02:00 — file + database, cifrati su S3, tenuti 14 giorni
$ cipi backup profile add nightly --scope=all \
      --cron='0 2 * * *' --keep-days=14 --dest=s3 --encrypt
bash
$ cipi backup profile list                 # tutti i profili
$ cipi backup profile show nightly         # un profilo in dettaglio
$ cipi backup profile edit nightly --keep-days=30
$ cipi backup profile disable hourly-db    # mettilo in pausa senza eliminarlo
$ cipi backup profile enable hourly-db
$ cipi backup profile remove hourly-db     # elimina il profilo, tiene gli archivi

Flag per profile add / profile edit

--scope=all|files|dbCosa prende il profilo: file applicazione, database, o entrambi.
--apps='shop,blog'Quali app coprono i suoi archivi file. Pattern glob ammessi.
--databases='main,tenant_*'Quali database copre. Vengono scoperti dal motore stesso, quindi anche i database tenant che un'app crea a runtime vengono matchati.
--exclude-databases='<glob,…>'Database da lasciare fuori da una selezione altrimenti ampia.
--exclude-tables='*.jobs,*.telescope_*'Tabelle da saltare — espanse contro la lista tabelle live su MariaDB, passate dritto a pg_dump su PostgreSQL.
--every=30m|6h|1d o --cron='0 2 * * *'Quanto spesso gira.
--dest=local|s3|local,s3Dove va la run.
--keep=N / --keep-days=N / --keep-weeks=NRetention — almeno una è obbligatoria. Un profilo che crescerebbe senza limite viene rifiutato.
--encrypt / --no-encryptCifratura AES-256 lato client prima che qualcosa lasci il server.
Le app multi-tenant ora sono coperte. Prima della 5.1.0 una run dumpava esattamente un database per app — quello col nome dell'app — quindi tenant_1, tenant_2, … non venivano mai salvati. I database ora arrivano dal motore (meno gli schema di sistema) e si selezionano con pattern glob.

3 — Cifratura

Con --encrypt l'archivio è cifrato con AES-256 sul server, prima dell'upload, così l'operatore del bucket non tiene mai dati leggibili. Il manifest resta leggibile così una run si può ancora identificare.

bash
$ cipi backup key show      # stampa la chiave — conservala off-server
$ cipi backup key rotate    # nuova chiave per le run future
Senza la chiave un backup cifrato non si può ripristinare — né tu, né Cipi. Salvala in un password manager nel momento in cui abiliti --encrypt, e ricorda che le run prese prima di un key rotate hanno ancora bisogno della vecchia chiave.

4 — Eseguire, controllare e ripristinare

bash
$ cipi backup run                          # esegui ora ogni profilo abilitato
$ cipi backup run --profile=nightly        # esegui ora un profilo
$ cipi backup run --dry-run                # mostra cosa prenderebbe, non prende nulla
$ cipi backup list [--profile=nightly]     # run tenute su ciascuna destinazione
$ cipi backup verify                       # la run più recente di ogni profilo si apre?
$ cipi backup verify --deep                # stesso, scaricando da S3 per controllare
$ cipi backup prune [--profile=nightly]    # applica la retention ora
$ cipi backup fetch nightly 2026-09-02_020000   # scarica e decifra una run

Dalla v5.1.0 questi comandi ti dicono la verità invece di rassicurarti:

  • Ogni archivio è controllato in integrità prima di partire. Un dump tagliato da un disco pieno è comunque un file non vuoto, quindi il vecchio check sulla size lo faceva passare; ora un archivio corrotto viene scartato e segnalato invece di sostituire in silenzio un backup buono.
  • cipi backup fetch non riporta più successo su un prefisso senza oggetti, quindi un timestamp sbagliato è un errore invece di una directory vuota.
  • cipi backup verify dice chiaramente che non c'è nulla da verificare quando non è ancora successa nessuna run, invece di “passed”.
  • Gli avvisi di tar — “file changed as we read it”, costanti su un'app live che scrive i log — non fanno più fallire un archivio perfettamente buono. Conta solo l'exit code 2 e oltre.
  • Un profilo disabilitato smette davvero di girare, e Encrypted è visualizzato correttamente.

Per ripristinare, fetcha la run e rimetti i pezzi:

bash
$ cipi backup fetch nightly 2026-09-02_020000 --dest=/root/restore
$ cipi db restore myapp /root/restore/databases/mariadb/myapp.sql.gz
$ tar -tzf /root/restore/apps/myapp/files.tar.gz

5 — Layout di storage

File applicazione e database sono salvati separatamente, con un manifest per run — così un profilo solo-database non costa nulla da prendere, e un database si può ripristinare senza spacchettare un'app.

text
<root>/<profile>/<YYYY-MM-DD_HHMMSS>/
├── manifest.json
├── apps/
│   └── myapp/
│       ├── files.tar.gz
│       └── meta.json
└── databases/
    └── mariadb/
        └── myapp.sql.gz

# local  → /var/backups/cipi/<profile>/<timestamp>/
# s3     → s3://<bucket>/cipi/<profile>/<timestamp>/

Lo staging dei backup defaulta su /var/tmp (disco) invece di /tmp (spesso un tmpfs RAM piccolo), così le app grandi non falliscono a metà backup quando il tmpfs si riempie. Override con tmpdir in backup.json (via cipi backup configure) o la variabile d'ambiente CIPI_BACKUP_TMPDIR.

6 — Schedule e watchdog di ritardo

Non scrivi più le righe cron a mano. cipi backup configure e ogni cambio di profilo riscrivono un blocco marcato nel crontab di root; qualsiasi cosa fuori da quel blocco resta intatta, e le righe pre-5.1 scritte a mano vengono assorbite in migration.

Un watchdog orario alza la notifica backup_stale quando un profilo non è riuscito entro il doppio del proprio intervallo — perché un backup che ha smesso di girare in silenzio è peggio di nessun backup: sembra ancora configurato. Un profilo appena creato non viene segnalato in ritardo prima che la prima run programmata possa essere successa.

Prune legacy

cipi backup prune <app> --weeks=N continua a funzionare contro il layout pre-5.1 (s3://<bucket>/cipi/<app>/<timestamp>/ più i dump pre-deploy in /var/log/cipi/backups), così gli archivi esistenti e qualsiasi riga cron scritta a mano fanno ancora prune. I profili nuovi usano --keep, --keep-days o --keep-weeks.

Un'app può dichiarare i propri profili di backup nel repository — vedi cipi.yml. I profili posseduti da un'app devono chiamarsi <app> o <app>-*; i profili server-wide restano sotto il tuo controllo.

Crontab utente

Cipi aggiunge automaticamente una voce crontab per lo scheduler Laravel quando crei un'app:

bash
# installed automatically by cipi app create
* * * * * /usr/bin/php8.5 /home/myapp/current/artisan schedule:run >> /dev/null 2>&1

Questa voce gira come utente Linux myapp ogni minuto, usando la versione PHP selezionata per l'app. Viene aggiornata automaticamente quando cambi versione PHP con cipi app edit myapp --php=X.

Visualizzare il crontab attuale

bash
# as root — view the app user's crontab
$ crontab -u myapp -l

# or after switching to the app user
$ su - myapp
myapp@server:~$ crontab -l

Aggiungere job cron personalizzati

Puoi aggiungere job cron extra al crontab dell'utente app. Passa prima all'utente app per assicurarti che i job girino con il contesto utente e i permessi file corretti:

bash
$ su - myapp
myapp@server:~$ crontab -e

Esempi di voci che potresti aggiungere:

bash
# existing Laravel scheduler (do not remove)
* * * * * /usr/bin/php8.5 /home/myapp/current/artisan schedule:run >> /dev/null 2>&1

# nightly database backup at 2 AM
0 2 * * * /usr/local/bin/cipi db backup myapp >> /home/myapp/logs/backup.log 2>&1

# custom script every 15 minutes
*/15 * * * * /home/myapp/current/scripts/sync.sh >> /home/myapp/logs/sync.log 2>&1
Non rimuovere la voce dello scheduler Laravel. Cipi non la re-inserisce automaticamente se eliminata — dovresti eseguire cipi app edit myapp --php=<current-version> per ripristinarla. Tieni sempre la riga schedule:run come prima voce così è facile identificarla.
I job cron girano come utente app. Rispettano le stesse restrizioni filesystem dell'app. Se un job cron deve scrivere file, assicurati che il percorso di destinazione sia dentro /home/myapp/. I job che richiedono accesso root vanno aggiunti al crontab di root, con crontab -e come root.

Verificare che cron funzioni

bash
# check system cron log
$ grep CRON /var/log/syslog | grep myapp | tail -20

# check Laravel scheduler execution
$ cipi app artisan myapp schedule:list

cipi schedule

Da v5.0, gestisci la voce crontab dello scheduler Laravel che esegue schedule:run (il crontab esisteva già; ora è attivabile/disattivabile e tracciato in apps.json).

bash
$ cipi schedule on myapp
$ cipi schedule off myapp
$ cipi schedule status myapp

cipi worker & Laravel Horizon

Ogni app ottiene un worker Supervisor predefinito per la queue default. Puoi aggiungere queue aggiuntive con conteggi processo e timeout personalizzati.

bash
$ cipi worker add myapp --queue=emails --processes=3
$ cipi worker add myapp --queue=exports --processes=1 --timeout=7200
$ cipi worker list myapp
$ cipi worker edit myapp --queue=default --processes=3
$ cipi worker remove myapp emails
$ cipi worker restart myapp   # restart all workers for the app
$ cipi worker stop myapp      # stop all workers for the app (used during deploys)

# Laravel Horizon (v5.0+) — mutually exclusive with queue:work workers
$ cipi worker horizon enable myapp
$ cipi worker horizon status myapp
$ cipi worker horizon disable myapp

Con Horizon abilitato, il deploy esegue horizon:terminate e riavvia i worker tramite cipi-worker. Non puoi far girare worker classici queue:work e Horizon sulla stessa app contemporaneamente.

Sulla 5.0.x, cipi worker horizon enable poteva lasciare Horizon mezzo abilitato: il comando non stampava nulla dopo “Enabling Horizon…” e status diceva ancora disabled. La v5.1.0 sistema entrambe le cause, scrive sempre lo stato, riporta cosa ha fatto davvero Supervisor, e fa sì che status mostri qualsiasi drift tra i due. Se ti è successo, esegui cipi self-update e riabilitalo.

I queue worker si possono anche dichiarare nel repository dell'app — vedi cipi.yml.

Flag Descrizione
--queue=<name> Nome della queue da consumare (es. default, emails, exports)
--processes=<n> Numero di processi worker paralleli
--timeout=<seconds> Timeout del job in secondi. Il default è 60.

I worker vengono fermati prima dello swap del symlink e riavviati dopo ogni deploy, evitando che Supervisor usi percorsi artisan obsoleti. Supervisor è configurato con autorestart=unexpected così i worker si riavviano solo in caso di uscita inattesa, non su stop graceful.

Helper utente app: cipi-worker

Ogni utente app può riavviare, fermare o controllare i worker senza root — tramite un helper sudo ristretto installato in /usr/local/bin/cipi-worker:

bash
# run as the app user (SSH or sudo su - myapp)
$ sudo cipi-worker status myapp
$ sudo cipi-worker stop myapp      # used by Deployer before symlink swap
$ sudo cipi-worker restart myapp

Come root, usa cipi worker list|restart|stop <app>. Non esiste un comando admin cipi worker status — usa cipi worker list o l'helper utente app sopra.

cipi health

Da v5.0, configura healthcheck HTTP per app. Un cron gira ogni 5 minuti; dopo 3 fallimenti consecutivi Cipi notifica tramite il trigger health_fail (SMTP se configurato).

bash
$ cipi health set myapp --url=https://myapp.com/up --expect=200
$ cipi health check myapp
$ cipi health list
$ cipi health unset myapp

# Output strutturato (v5.0.6+) — panel API / script
$ cipi health list --json
$ cipi health check myapp --json

Verifica post-deploy (v5.1.0+)

Una volta che un'app ha un URL di healthcheck, la release appena andata live viene verificata subito dopo ogni deploy — sia da cipi deploy sia dal webhook Git. Il probe aspetta un breve grace period (8 secondi per le app Octane, 3 altrimenti, o quanto dice --grace=N) e riprova cinque volte, così un'app che ha bisogno di un attimo per alzarsi non viene segnalata come rotta.

Il verdetto non cambia mai l'exit code del deploy — la release è live in ogni caso — ma l'alert lo dice e ti dà il comando di rollback. L'email di successo parte dopo la verifica, quindi non può mai annunciare un deploy riuscito mentre il sito risponde 500.

bash
$ cipi health postdeploy myapp             # esegui ora la verifica post-deploy
$ cipi health set myapp --grace=15         # dai più tempo alla release per scaldarsi (max 120)
$ cipi health set myapp --no-postdeploy    # spegni il check post-deploy per questa app

Auto-rollback di una release unhealthy (opt-in)

Cipi può annullare una release che fallisce l'healthcheck post-deploy: il symlink current torna alla release precedente, l'app viene probeata di nuovo, e una email descrive l'intera sequenza — cosa è stato pubblicato, cosa ha risposto, a cosa è stato rolled back e se questo l'ha sistemata.

bash
$ cipi health set myapp --rollback-on-unhealthy   # permanente, per app
$ cipi deploy myapp --rollback-on-unhealthy       # solo questo deploy

Quattro esiti sono riportati in modo distinto: recovered; rolled back ma ancora unhealthy (quindi la causa probabilmente non è il codice); il rollback stesso è fallito (la release cattiva è ancora live); e non c'è una release precedente a cui tornare.

L'auto-rollback è off di default e di proposito: le migration del database non vengono disfatte. Una release che ha migrato lo schema e poi è fallita può stare peggio dopo che il codice è tornato indietro. Abilitalo solo per app i cui deploy non migrano, o dove sai che le migration sono backwards-compatible.

REST: GET /api/health, GET|PUT|DELETE /api/apps/{name}/health, POST /api/apps/{name}/health/check (API 1.15.0+ / Cipi 5.0.6+). Un'app può anche dichiarare il suo healthcheck nel repository — vedi cipi.yml.

cipi firewall

Cipi installa UFW con le porte 22, 80 e 443 aperte di default. Usa i comandi firewall per gestire regole aggiuntive senza toccare UFW direttamente.

bash
$ cipi firewall allow 3306                  # open a port
$ cipi firewall allow 3306 --from=10.0.0.5  # allow from specific IP
$ cipi firewall allow 3306 --from=10.0.0.0/24 # allow from subnet
$ cipi firewall deny 8080                   # block a port
$ cipi firewall list                        # show all rules

cipi ban

Ispeziona e gestisci i ban Fail2ban direttamente dalla CLI. Cipi configura Fail2ban con ban progressivi: ban base di 24 ore che raddoppia a ogni recidiva fino a un tetto di 7 giorni, con tentativi massimi ridotti a 3. Una jail dedicata recidive banna i recidivi per 7 giorni dopo 3 ban entro 24 ore.

bash
$ cipi ban list                        # list all banned IPs, grouped by jail
$ cipi ban unban 203.0.113.42           # unban a specific IP from all jails

cipi ban list

Elenca ogni IP attualmente bannato da Fail2ban, raggruppato per jail (es. sshd, recidive). Utile per un controllo rapido della sicurezza o prima di un unban.

cipi ban unban <IP>

Rimuove l'IP indicato da tutte le jail Fail2ban in un colpo solo. Comodo quando un utente legittimo o un runner CI viene bloccato per errore.

Le installazioni esistenti vengono aggiornate automaticamente dallo script di migrazione 4.3.0 quando esegui cipi self-update. Non serve configurazione manuale.

cipi service

Controlla e gestisci i servizi di sistema che alimentano Cipi direttamente dalla CLI. Nginx usa un reload graceful (zero downtime) invece di un restart completo.

bash
$ cipi service list                    # status of all services
$ cipi service list nginx              # status of a specific service
$ cipi service restart                 # restart all services
$ cipi service restart nginx           # graceful reload (zero downtime)
$ cipi service restart php             # restart all PHP-FPM versions
$ cipi service start fail2ban
$ cipi service stop supervisor         # asks for confirmation

# Output strutturato (v5.0.6+) — panel API
$ cipi service list --json

REST: GET /api/services, POST /api/services/{name}/restart (API 1.15.0+ / Cipi 5.0.6+; ability services-view / services-manage).

Nomi servizio supportati: nginx, mariadb, postgresql (alias: pgsql, postgres — se installato via cipi db install pgsql), valkey-server, supervisor, fail2ban, php<ver>-fpm (es. php8.5-fpm). La keyword php punta a tutte le versioni PHP-FPM installate in una volta. Per il backend cache, redis-server, redis e valkey sono accettati come alias di valkey-server.

Valkey — il fork compatibile Redis con licenza BSD — è incluso nello stack predefinito e sostituisce redis-server da Cipi 4.5.6. È installato con password, legato solo a localhost, e le credenziali (utente, password) sono salvate in /etc/cipi/server.json e mostrate a fine installazione. valkey-server è aggiunto alla blacklist di unattended-upgrades — Cipi lo gestisce, quindi non viene aggiornato automaticamente. Vedi la sezione Valkey per i dettagli e la migrazione automatica Redis → Valkey.

cipi ssh — Gestione chiavi SSH

Gestisci le chiavi SSH autorizzate per l'utente cipi — il punto di ingresso SSH admin. L'utente cipi (gruppo cipi-ssh) usa solo chiave pubblica; il login root è disabilitato. Gli utenti app (gruppo cipi-apps) si connettono con password — vedi SSH come utente app.

Comandi

bash
$ cipi ssh list                 # list all authorized keys with fingerprint, comment, and current-session marker
$ cipi ssh add [key]             # add a new SSH public key (validates format, prevents duplicates)
$ cipi ssh remove [n]            # remove a key by number
$ cipi ssh rename [n] [name]     # change the display name / comment of a key

# Output strutturato (v5.0.6+) — panel API
$ cipi ssh list --json

REST: GET|POST /api/ssh/keys, DELETE /api/ssh/keys/{n} (API 1.15.0+ / Cipi 5.0.6+).

Meccanismi di sicurezza

cipi ssh remove include due salvaguardie per evitare il lockout:

  • Protezione sessione corrente — non puoi rimuovere la chiave usata dalla tua sessione SSH attiva.
  • Protezione ultima chiave — non puoi rimuovere l'ultima chiave autorizzata rimasta.

Commenti delle chiavi

Le chiavi SSH sono memorizzate con i commenti originali intatti, così è facile capire a chi appartiene ogni chiave. Usa cipi ssh rename per cambiare il nome visualizzato di una chiave:

bash
# list keys to find the number
$ cipi ssh list

# rename key #2
$ cipi ssh rename 2 "john-macbook"

Notifiche email

Quando SMTP è configurato, Cipi invia un avviso email ogni volta che una chiave viene aggiunta, rimossa o rinominata. La notifica include hostname del server, indirizzo IP, fingerprint della chiave, commento della chiave, timestamp e conteggio chiavi rimanenti. Le notifiche di rename includono anche il vecchio e il nuovo nome della chiave.

cipi — Server e self-update

Comandi di top level per lo stato del server e l'auto-gestione di Cipi.

bash
$ cipi status              # CPU, RAM, disk, services, PHP versions, apps
$ cipi version             # show installed Cipi version
$ cipi self-update         # update Cipi to the latest version
$ cipi self-update --check # check for updates without installing

Reset password e credenziali

Cipi fornisce comandi per rigenerare le password a livello server. Le nuove password sono memorizzate in /etc/cipi/server.json (crittografate via Vault) e mostrate a schermo. Salvale subito — vengono mostrate una sola volta.

bash
$ cipi reset root-password              # regenerate the root Linux user SSH password
$ cipi reset db-password [--engine=…]   # regenerate root password (default or chosen engine)
$ cipi reset valkey-password           # regenerate the Valkey password and restart the service
cipi reset valkey-password (alias cipi reset redis-password) riavvia il servizio Valkey. I client connessi verranno disconnessi temporaneamente. Se le tue app usano Valkey per cache o sessioni, aspettati una breve interruzione.
