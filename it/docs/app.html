App

cipi app create

cipi app create supporta due tipi di app: Laravel (predefinito) e Custom (--custom). Le app Laravel ottengono un ambiente completamente isolato: utente Linux, pool PHP-FPM oppure Laravel Octane (FrankenPHP) dalla v5.0, vhost Nginx, database (MariaDB di default; PostgreSQL opzionale dalla v4.8.0), queue worker Supervisor, voce crontab, release Deployer zero-downtime, chiave deploy SSH e .env compilato automaticamente. Le app personalizzate sono più semplici — vedi app personalizzate per i dettagli.

App Laravel (predefinita — PHP-FPM)

bash
$ cipi app create

Laravel Octane (FrankenPHP)

bash
$ cipi app create --octane
$ cipi app create --octane=frankenphp   # explicit (same as --octane)

Vedi Laravel Octane per i requisiti, la conversione e come il vhost differisce da FPM.

Non interattivo (flag)

bash
$ cipi app create \
    --user=myapp \
    --domain=myapp.com \
    --repository=git@github.com:you/myapp.git \
    --branch=main \
    --php=8.5

# Laravel Octane (FrankenPHP) — v5.0+
$ cipi app create --user=myapp --domain=myapp.com \
    --repository=git@github.com:you/myapp.git --octane

# optional PostgreSQL (v4.8.0+, after cipi db install pgsql)
$ cipi app create --user=myapp --domain=myapp.com \
    --repository=git@github.com:you/myapp.git --engine=pgsql
--userNome utente Linux per l'app. Deve essere univoco, minuscolo, alfanumerico.
--domainDominio principale (es. myapp.com). Usato per il vhost Nginx e APP_URL.
--repositoryURL Git SSH (es. git@github.com:you/repo.git). Deve essere SSH, non HTTPS.
--branchBranch da deployare. Predefinito: main.
--phpVersione PHP per questa app (es. 8.5). Predefinito PHP 8.5. Deve essere una versione installata — solo 8.3, 8.4 e 8.5 sono accettate dalla v4.5.4 (Deployer 8 richiede PHP ≥ 8.3).
--octane / --octane=frankenphpServe HTTP via Laravel Octane (FrankenPHP) invece di PHP-FPM (dalla v5.0). Solo app Laravel — rifiutato con --custom. Vedi Laravel Octane.
--engineMotore database: mariadb (predefinito) o pgsql (dalla v4.8.0; richiede cipi db install pgsql). La creazione interattiva chiede quando PostgreSQL è installato. Scrive .env / URL di connessione corrispondenti.
Se è configurato un token GitHub o GitLab, Cipi aggiunge automaticamente la chiave deploy SSH e crea il webhook sul repository — nessun passaggio manuale. Vedi Git auto-setup per le istruzioni di configurazione e le opzioni di fallback quando l'auto-configurazione non è disponibile.

App

Laravel Octane (FrankenPHP)

Dalla v5.0, le app Laravel possono servire HTTP via Laravel Octane con il server FrankenPHP invece di un pool PHP-FPM per app. Octane e le app FPM classiche convivono sullo stesso server Cipi.

Cosa configura Cipi

  • Alloca una porta localhost in 8100–8999 e salva octane / octane_port in apps.json
  • Il vhost Nginx usa proxy_pass verso Octane e serve i file statici da current/public — nessun pool FPM per app
  • Programma Supervisor ${app}-octane accanto ai queue worker
  • Il template Deployer laravel-octane.php riavvia / ricarica Octane al deploy
  • .env: OCTANE_SERVER=frankenphp, OCTANE_HTTPS=true

Requisiti dell'app

Il tuo repository Laravel deve includere laravel/octane ed eseguire php artisan octane:install --server=frankenphp. Octane parte dopo il primo deploy riuscito.

bash
# create an Octane app
$ cipi app create --user=myapp --domain=myapp.com \
    --repository=git@github.com:you/myapp.git --octane

# convert an existing FPM app → Octane (or the reverse)
$ cipi app convert myapp --to=octane
$ cipi app convert myapp --to=fpm

# tune Octane workers (also see app limits)
$ cipi app limits myapp --octane-workers=4

cipi app convert --to=octane|fpm riscrive pool / vhost / Supervisor / template Deployer / .env e riapplica SSL quando un certificato è già presente.

Suggerimento Octane: mantieni il lavoro queue di lunga durata su cipi worker o Horizon — Octane gestisce solo HTTP. Abbinalo a Reverb per i WebSocket.

cipi app create --custom

Crea un'app personalizzata con deploy classico (senza zero-downtime): il codice viene deployato in htdocs — nessun symlink current/shared. Ideale per siti statici, SPA (Vue, React, Svelte), WordPress, altri CMS o qualsiasi progetto PHP non Laravel o framework.

Durante la creazione scegli solo la document root (predefinito /, oppure es. www, dist, public). Nginx è preconfigurato con index index.html index.php, try_files $uri $uri/ /index.php?$args e error_page 404 /404.html — nessuna richiesta per try_files o entry point.

Git opzionale (solo SFTP)

Il repository Git è opzionale per le app personalizzate. Le app Laravel richiedono ancora un repository. Se salti il repository per un'app personalizzata, Cipi crea /home/<app>/htdocs con un index.html segnaposto e non configura chiave deploy o webhook — carichi i file con SFTP (o SCP/rsync) in ~/htdocs come utente dell'app. L'output di onboarding spiega questo flusso “no repo — solo SFTP”. Se fornisci un repository, il comportamento resta invariato: usa cipi deploy <app> per scaricare il codice in htdocs.

Cosa è incluso e cosa aggiungi tu

Le app personalizzate non hanno database, nessun .env, nessun cron e nessun queue worker. Quando un repository è configurato, vengono mostrati chiave deploy e (con Git auto-setup) webhook; per le app solo SFTP, vengono omessi. Il riepilogo post-creazione elenca l'accesso SSH e i passi successivi di conseguenza.

Se la tua app personalizzata necessita di un database (es. WordPress, Drupal), creane uno con cipi db create --name=<app> dopo il deploy. Vedi cipi db per backup, restore e gestione password.

Con Git — esempio non interattivo:

bash
$ cipi app create --custom --user=mysite --domain=mysite.com \
    --repository=git@github.com:you/mysite.git --docroot=dist

Solo SFTP — ometti --repository e --branch:

bash
$ cipi app create --custom --user=mysite --domain=mysite.com --docroot=dist

Con un repository, usa cipi deploy <app> per fare il deploy; il codice viene clonato in /home/<app>/htdocs.

cipi app fix-permissions

Il pannello aveva già cipi api fix-permissions e cipi gui fix-permissions; le app no. Un chown -R app:app /home/<app> è sbagliato: nginx scrive i log del vhost come www-data in logs/ (2775 setgid), la home deve restare 750 così www-data (nel gruppo dell'app) può leggere il docroot, .ssh deve essere 700 o OpenSSH StrictModes rifiuta la deploy key, e shared/.env è 640. Questo comando riapplica quel layout — ownership dell'albero tranne logs/, poi l'helper log/ACL, directory storage 775, Composer auth.json 640, cipi-databases.env 600. Un'app nominata, o ogni app.

bash
$ cipi app fix-permissions myapp
$ cipi app fix-permissions          # ogni app su questo server

cipi deploy esegue già l'helper log-ACL prima di Deployer. fix-permissions è l'intera home, a richiesta, dopo che qualcuno ha scompattato uno zip come root o ha messo .ssh a 775. Disponibile dalla v5.2.1. Nessuna migration: cipi self-update copia le lib e aggiorna il completamento della shell. Il file sudoers del pannello elenca il nuovo comando così una futura GUI può invocarlo; i server esistenti prendono quella riga al prossimo rewrite dei sudoers (la CLI gira come root e non ne ha bisogno).

cipi app reverb

Laravel Reverb è il server WebSocket first-party di Laravel. Cipi lo gestisce dalla v5.0; la v5.1.2 è la release che lo ha reso utilizzabile in produzione: credenziali generate, schema derivato dal certificato, limiti di connessione alzati e una regola di proxy che non intercetta più le rotte dell'applicazione.

Abilitare Reverb su un'app Laravel configura quattro cose:

127.0.0.1:9000–9099Una porta localhost libera, allocata per app e registrata in apps.json. Reverb non è mai in ascolto su un'interfaccia pubblica.
${app}-reverbUn programma Supervisor che esegue artisan reverb:start come utente dell'app, con log in /home/<app>/logs/reverb.log.
nginxUn blocco proxy sul dominio dell'app per /app/{key} (l'handshake WebSocket) e /apps/{id}/… (l'API HTTP usata dall'applicazione per fare broadcast).
.envREVERB_* e VITE_REVERB_*, generati alla prima abilitazione e mai ruotati in seguito.
bash
$ cipi app reverb enable myapp
$ cipi app reverb enable myapp --restart-supervisor   # applica subito il nuovo limite di file aperti
$ cipi app reverb status myapp
$ cipi app reverb disable myapp
--restart-supervisorRiavvia Supervisor durante enable, così il nuovo limite di file descriptor si applica subito. Questo riavvia tutti i queue worker del server: per questo Cipi non lo fa mai di sua iniziativa.

Reverb è solo per app Laravel: enable rifiuta un'app --custom. Rieseguire enable su un'app che ha già Reverb è sicuro e utile: non rialloca la porta e non tocca le credenziali, ma ricalcola host e schema pubblici e ripristina le chiavi .env eventualmente mancanti.

Abilitarlo dall'inizio alla fine

bash
# 1. Nel progetto, in locale — installa il pacchetto e la parte client, poi committa.
#    `install:broadcasting` crea resources/js/echo.js e config/reverb.php.
$ composer require laravel/reverb
$ php artisan install:broadcasting

# 2. Sul server — porta, programma Supervisor e proxy nginx.
$ cipi app reverb enable myapp

# 3. Un certificato, così i client usano wss:// invece di ws:// (salta se l'app ne ha già uno).
$ cipi ssl install myapp

# 4. Deploy: composer install, build Node, poi Reverb riparte sulla nuova release.
$ cipi deploy myapp
$ cipi app reverb status myapp

L'ordine conta solo per un punto: la build Node deve girare dopo reverb enable, perché Vite incorpora VITE_REVERB_* nel bundle in fase di build. Lo step node_build di Cipi viene eseguito dopo che Deployer ha collegato il .env condiviso, quindi un deploy successivo all'enable produce un frontend che trova davvero il socket. Se in seguito cambi dominio o installi un certificato, serve un altro deploy perché il bundle si allinei.

Cosa scrive Cipi nel .env

env
# Laravel Reverb — gestito da Cipi (cipi app reverb status myapp)
# Dove ascolta il programma Supervisor. Questa coppia è interamente di Cipi.
REVERB_SERVER_HOST=127.0.0.1
REVERB_SERVER_PORT=9000

BROADCAST_CONNECTION=reverb

# Generate una volta sola alla prima abilitazione, poi mai più toccate.
REVERB_APP_ID=482913
REVERB_APP_KEY=3f9c1ab27de40518b6c4
REVERB_APP_SECRET=a71f0e5c8d24b93a6f10c7e5482db9af

# Il lato pubblico — derivato da ciò che nginx serve davvero.
REVERB_HOST=myapp.com
REVERB_PORT=443
REVERB_SCHEME=https

# Lette da Vite in fase di build e incorporate nel bundle frontend.
VITE_REVERB_APP_KEY="${REVERB_APP_KEY}"
VITE_REVERB_HOST="${REVERB_HOST}"
VITE_REVERB_PORT="${REVERB_PORT}"
VITE_REVERB_SCHEME="${REVERB_SCHEME}"

Prima della 5.1.2 le tre credenziali restavano vuote, da inventare a mano — e un REVERB_APP_KEY vuoto è esattamente ciò che impedisce a reverb:start di partire. Ora vengono generate al primo enable e un valore già presente vince sempre, quindi un'app che arriva con le proprie credenziali le mantiene. Cipi non le ruota mai: una chiave nuova disconnetterebbe tutti i client attivi e invaliderebbe qualsiasi bundle frontend già compilato con la vecchia.

Collegarsi dal frontend

Il resources/js/echo.js standard generato da install:broadcasting legge già esattamente le variabili che Cipi scrive — non c'è nulla da modificare:

js
import Echo from 'laravel-echo';
import Pusher from 'pusher-js';

window.Pusher = Pusher;

window.Echo = new Echo({
    broadcaster: 'reverb',
    key: import.meta.env.VITE_REVERB_APP_KEY,
    wsHost: import.meta.env.VITE_REVERB_HOST,
    wsPort: import.meta.env.VITE_REVERB_PORT ?? 80,
    wssPort: import.meta.env.VITE_REVERB_PORT ?? 443,
    forceTLS: (import.meta.env.VITE_REVERB_SCHEME ?? 'https') === 'https',
    enabledTransports: ['ws', 'wss'],
});

Poiché nginx espone Reverb sul dominio e sulla porta dell'app, non c'è nessuna porta extra da aprire nel firewall né un secondo certificato da gestire. cipi app reverb status stampa l'URL esatto che il client finisce per contattare.

/app e /apps appartengono al protocollo. Fino alla 5.1.1 il proxy era scritto come location /app, che in nginx è un match per prefisso, non per path: su ogni app con Reverb attivo /appuntamenti, /apple e /application/… finivano dentro Reverb invece di arrivare a Laravel. Dalla 5.1.2 il blocco è la regex ~ ^/apps?(/|$), che intercetta solo /app/{key} e /apps/{id}/…. Un'app che ha una propria rotta /app o /apps continua a non poter usare Reverb sullo stesso dominio: mettila su un sottodominio dedicato.

ws:// o wss://

Cipi deriva host, porta e schema pubblici da ciò che il server serve davvero, invece di dare per scontato HTTPS:

nessun certificatohttp sulla porta 80 — l'app è servita in HTTP, quindi il socket è ws://.
certificato presentehttps sulla porta 443 — wss://.
dominio wildcard*.example.com viene risolto in un host concreto (www.example.com), perché nessun browser può aprire un socket verso un wildcard. Un frontend multi-tenant deve scegliere il proprio host a runtime.

Installare un certificato in un secondo momento — HTTP-01 o DNS-01 — sposta subito le impostazioni Reverb dell'app su wss://, e anche un cambio di dominio le ricalcola. Prima della 5.1.2 questi valori erano fissati a https/443 al momento dell'enable: su un'app senza certificato il browser rifiutava silenziosamente la connessione come mixed content, senza nulla nel log di Reverb a spiegarlo. Ora reverb status avvisa quando l'app ha un certificato ma il .env dice ancora ws://.

Connessioni concorrenti e file aperti

Ogni WebSocket aperto costa un file descriptor dentro Reverb e due connessioni dentro nginx: il limite soft di default di 1024 ferma l'app intorno ai mille client concorrenti, senza che nessun log ne spieghi il motivo. Dalla 5.1.2 Cipi alza entrambi i tetti:

SupervisorUn drop-in systemd in /etc/systemd/system/supervisor.service.d/cipi-nofile.conf con LimitNOFILE=65535, ereditato da ogni programma gestito da Supervisor.
nginxworker_rlimit_nofile 65535 e worker_connections 8192 in nginx.conf, applicati con un reload.

nginx recepisce i nuovi limiti con il reload che Cipi esegue. Supervisor invece li recepisce solo a un riavvio, che riavvia anche tutti i queue worker del server: Cipi quindi prepara il drop-in, avvisa che è in attesa e lascia a te la decisione.

bash
$ systemctl restart supervisor
# oppure, in un colpo solo, al momento dell'enable:
$ cipi app reverb enable myapp --restart-supervisor

Un altro limite silenzioso era il timeout di lettura del proxy: valeva esattamente quanto l'intervallo di ping di Reverb (60 secondi), quindi ogni client inattivo era un testa o croce tra il ping e il timeout. Ora è ampiamente più alto, e a chiudere le connessioni morte è il ciclo di ping/prune di Reverb, che è esattamente il suo compito.

cipi app reverb status

Riporta la porta, cosa sta facendo Supervisor con il processo, l'URL che il client dovrebbe contattare e i tre problemi che non lasciano traccia in nessun log:

bash
$ cipi app reverb status myapp
  Reverb: enabled 127.0.0.1:9000
myapp-reverb                     RUNNING   pid 21847, uptime 3 days, 4:12:07
  Clients dial: wss://myapp.com:443/app/3f9c1ab27de40518b6c4
  Open files: 65535 (supervisor)
Missing in .env: …Una credenziale è assente o vuota: reverb:start non parte. Riesegui cipi app reverb enable.
certificate but REVERB_SCHEME is 'http'L'app ha ottenuto un certificato dopo l'abilitazione di Reverb. Riesegui enable per passare a wss://, poi fai un deploy perché il bundle si allinei.

Il log del processo è /home/<app>/logs/reverb.log, e supervisorctl status myapp-reverb / restart myapp-reverb controllano direttamente il programma.

Disabilitare

cipi app reverb disable ferma e rimuove il programma Supervisor, rigenera il vhost senza il blocco proxy, riapplica SSL e — dalla 5.1.2 — riporta BROADCAST_CONNECTION al driver che l'app usava prima di Reverb, con log come fallback. Prima lasciava BROADCAST_CONNECTION=reverb, quindi ogni broadcast falliva contro un server che non era più in esecuzione.

Dal .env vengono rimosse solo REVERB_SERVER_HOST e REVERB_SERVER_PORT. Le credenziali restano: sono ciò da cui dipendono una riabilitazione — o un bundle frontend già compilato su di esse.

Clonazione e cipi.yml

cipi app clone copiava le chiavi REVERB_* dell'app sorgente nel .env del clone — puntando il frontend di staging al socket di produzione e consegnandogli il secret di produzione — senza però avviare alcun Reverb per esso. Dalla 5.1.2 un'app Reverb clonata ottiene porta, credenziali e dominio propri, esattamente come già otteneva il proprio Octane.

Reverb si può anche dichiarare nel file di progetto con workers.reverb: true|false: viene pianificato e applicato da cipi yml apply come Horizon e i queue worker, ed emesso da cipi yml generate. Dichiararlo su un'app --custom viene rifiutato in partenza.

yaml
workers:
  horizon: false
  reverb: true             # aggiunge un server WebSocket Reverb a questa app
Stai aggiornando da 5.0.x o 5.1.1? cipi self-update esegue la migrazione 5.1.2, che alza entrambi i limiti (segnalando se Supervisor ha ancora bisogno di un riavvio), riscrive il vhost di ogni app la cui location Reverb è ancora il prefisso ingordo /app — con backup in /var/lib/cipi/vhost-backup-5.1.2, verifica con nginx -t, SSL riapplicato e rollback dell'intero blocco in caso di errore — e completa le chiavi .env mancanti senza sovrascrivere nulla di già presente, così un'app con impostazioni socket sistemate a mano le conserva. Dopo l'aggiornamento fai un nuovo deploy delle app con Reverb, perché il bundle frontend recepisca i valori VITE_REVERB_*.

cipi app clone

Dalla v5.0, clona un'app Laravel esistente in una nuova app staging (o review) con dominio proprio. Imposta cloned_from in apps.json; non copia webhook o ID git. Se la sorgente ha Reverb, il clone ottiene porta, credenziali e host pubblici propri (dalla v5.1.2) — non eredita più il socket di produzione. Vedi cipi app reverb.

bash
$ cipi app clone myapp --domain=staging.myapp.com
$ cipi app clone myapp --domain=staging.myapp.com --name=myapp-stg --branch=develop --with-db
$ cipi app clone myapp --domain=staging.myapp.com --no-db
--domainObbligatorio. Dominio principale per la nuova app.
--nameNome utente Linux opzionale per il clone.
--branchBranch di deploy per il clone (predefinito: branch dell'app sorgente).
--with-dbCrea un database nuovo per il clone.
--no-dbSalta il provisioning del database per il clone.

cipi app limits

bash
$ cipi app limits myapp --fpm-max-children=20 --memory-limit=256M
$ cipi app limits myapp --octane-workers=4 --worker-procs=3
$ cipi app limits myapp   # show current limits
--fpm-max-childrenpm.max_children PHP-FPM per app FPM.

app suspend / app unsuspend

Disponibile dalla v4.5.8. Metti un'app offline senza eliminarla — utile per blocchi di fatturazione, finestre di manutenzione o siti staging che vuoi completamente spenti. La sospensione sostituisce il vhost Nginx con una pagina statica HTTP 503 servita da /var/www/cipi-suspended/.

bash
$ cipi app suspend myapp      # take offline (503 page)
$ cipi app unsuspend myapp    # restore normal vhost
Comando Descrizione
cipi app suspend <app> Imposta suspended: true in apps.json, ricostruisce il vhost per restituire 503 a tutte le richieste. Idempotente se già sospesa.
cipi app unsuspend <app> Rimuove il flag, ripristina il vhost Laravel/personalizzato normale e riapplica i blocchi SSL. Idempotente se già online.

Comportamento

  • HTTPS incluso — certbot clona il vhost di sospensione nel blocco :443, quindi anche HTTPS mostra la pagina offline
  • Let's Encrypt funziona ancora — il percorso /.well-known/acme-challenge/ resta pubblico così i certificati possono essere emessi o rinnovati mentre l'app è sospesa
  • Sopravvive alla rigenerazione del vhost — cambi alias, modifiche PHP e installazioni SSL rispettano il flag suspended
  • Visibile negli elenchi — cipi app list segna le app sospese; cipi domains aggiunge ⏸ suspended su ogni riga
Sospensione vs basic auth: cipi basicauth mostra un prompt di login ma esegue ancora la tua app. app suspend ferma PHP del tutto e serve una pagina offline statica — i visitatori non raggiungono mai Laravel. Usa suspend per “sito chiuso”; basic auth per “anteprima su invito”.

Disponibile anche via REST API (POST /api/apps/{name}/suspend), cipi-cli (apps suspend) e il modulo WHMCS (pulsanti Suspend / Unsuspend). Richiede l'abilità token apps-suspend per l'accesso API.

cipi basicauth

Disponibile dalla v4.5.2. Proteggi qualsiasi app — Laravel o personalizzata — dietro un prompt username/password Nginx. Utile per siti staging, tool interni o app non ancora pronte al traffico pubblico.

Comando Descrizione
cipi basicauth enable <app> [--user=NAME] [--password=PASS] Attiva HTTP basic auth. Le credenziali vengono generate se omesse e mostrate una sola volta a schermo — salvale subito
cipi basicauth disable <app> Rimuove il prompt e cancella le credenziali salvate
cipi basicauth status <app> Mostra se basic auth è attivo e l'utente configurato

Le credenziali sono hashate con openssl passwd -apr1 (non serve apache2-utils) e salvate in /etc/nginx/cipi-basicauth/<app>.htpasswd; lo stato attivo è in apps.json. Le direttive auth_basic sono iniettate per blocco location, quindi la protezione sopravvive alla rigenerazione del vhost (cambi alias, modifiche PHP) ed è clonata nel blocco :443 da certbot — HTTPS coperto. Le challenge ACME restano pubbliche, quindi emissione e rinnovo certificati non sono mai bloccati. Basic auth viene rimosso automaticamente con cipi app delete.

È distinto da cipi auth, che gestisce il auth.json di Composer per repository di pacchetti privati.

Gestione variabili ENV

Ogni app Laravel ha un unico file .env in /home/<app>/shared/.env. Le app personalizzate non hanno .env. Viene creato e precompilato da Cipi durante app create con credenziali database, APP_KEY, APP_URL, impostazioni cache/session/queue e token webhook. La directory shared/ è symlinkata in ogni release, quindi lo stesso .env è sempre attivo indipendentemente dalla release corrente.

Modifica interattiva via CLI

Il modo più sicuro per cambiare valori ENV è tramite Cipi — apre il file in nano come utente dell'app, con i permessi corretti:

bash
$ cipi app env myapp

Salva con Ctrl+O poi esci con Ctrl+X. Le modifiche hanno effetto immediato per le nuove richieste — nessun restart per la maggior parte dei valori. Se cambi connessione queue o driver cache, riavvia i worker:

bash
$ cipi worker restart myapp

Flag non interattivi (v5.0.3+)

Da v5.0.3, script, panel API e web GUI possono gestire il .env senza aprire un editor:

bash
$ cipi app env myapp --show
$ cipi app env myapp --show --json
$ cipi app env myapp --get=APP_URL
$ cipi app env myapp --set=APP_DEBUG=false
$ cipi app env myapp --unset=LEGACY_KEY

REST: GET|PUT /api/apps/{name}/env (ability apps-env, API 1.14+). MCP: AppEnvShow, AppEnvUpdate.

Modifica direttamente via SSH

Puoi anche modificare il file direttamente via SSH come root o come utente dell'app:

bash
# as root
$ nano /home/myapp/shared/.env

# or switch to the app user first
$ su - myapp
$ nano ~/shared/.env

Aggiungere le tue variabili

Aggiungi qualsiasi variabile personalizzata in fondo al file come faresti normalmente in un progetto Laravel. Sono preservate tra i deploy perché il .env vive in shared/ e non viene mai sovrascritto da Deployer.

env
# your custom variables
STRIPE_KEY=sk_live_...
STRIPE_SECRET=sk_live_...
MAIL_MAILER=smtp
MAIL_HOST=smtp.mailgun.org

cipi app run

Da v5.0.3, esegui un comando non interattivo in whitelist come utente dell'app — utile da CLI, panel API e “App commands” della web GUI. Editor, pager, shell e REPL sono bloccati (nano, vim, less, bash, tinker, …). Flag interattivi (es. tail -f, php -a) vengono rifiutati.

bash
$ cipi app run myapp composer install --no-dev
$ cipi app run myapp npm ci
$ cipi app run myapp ls -la shared
$ cipi app run --commands          # elenca i binari consentiti
$ cipi app run --commands --json

I binari consentiti includono composer, npm/npx/yarn/pnpm, ls/ll, cat/head/tail, helper filesystem, archivi, git, php, node e find. REST: POST /api/apps/{name}/run (job async, ability apps-run) e GET /api/run-commands (API 1.14+). MCP: AppRun, AppRunCommands.

v5.0.4+ ha corretto /usr/bin/env: '--': No such file or directory — ogni comando in whitelist (inclusi App commands della GUI) falliva prima di quella patch. Esegui cipi self-update.

cipi app logs

Segui i log applicativi in tempo reale. I log ruotano giornalmente e restano 14 giorni. Per default vengono mostrati tutti i log inclusi i log giornalieri Laravel (laravel-YYYY-MM-DD.log) da shared/storage/logs/.

bash
$ cipi app logs myapp                  # all logs (incl. Laravel daily logs)
$ cipi app logs myapp --type=nginx     # Nginx access + error
$ cipi app logs myapp --type=php       # PHP-FPM errors
$ cipi app logs myapp --type=worker    # queue worker output
$ cipi app logs myapp --type=deploy    # deploy history
$ cipi app logs myapp --type=laravel   # Laravel application logs
--type=nginxLog accesso ed errore Nginx
--type=phpLog errori PHP-FPM
--type=workerOutput Supervisor / queue worker
--type=deployOutput Deployer — cronologia deploy completa con timestamp
--type=laravelLog applicativi Laravel da shared/storage/logs/ (rotazione giornaliera laravel-YYYY-MM-DD.log)

app artisan & app tinker

Esegui comandi Artisan e Tinker come utente dell'app con la versione PHP corretta e contesto open_basedir — esattamente come girerebbero durante un deploy.

bash
$ cipi app artisan myapp migrate:status
$ cipi app artisan myapp queue:retry all
$ cipi app artisan myapp db:seed --class=ProductionSeeder
$ cipi app artisan myapp cache:clear
$ cipi app tinker myapp

SSH come utente dell'app

Ogni app gira sotto un utente Linux isolato. A volte devi lavorare direttamente nell'ambiente di quell'utente — ispezionare file, eseguire script one-off o debuggare qualcosa che si riproduce solo come utente corretto.

SSH diretto come utente dell'app (consigliato)

Gli utenti app possono fare SSH direttamente al server con la password generata alla creazione dell'app:

bash
# connect as the app user (password auth)
$ ssh myapp@your-server-ip

# you are directly inside the app user's shell
myapp@server:~$ pwd
/home/myapp

myapp@server:~$ cd ~/current
myapp@server:~$ ls

La password viene mostrata quando l'app viene creata (o usa cipi app reset-password myapp per rigenerarla). Funziona per client SFTP, sessioni remote IDE e accesso terminale.

Via cipi (percorso admin)

Se sei già connesso come cipi, puoi passare direttamente a qualsiasi utente app:

bash
$ ssh cipi@your-server-ip
cipi@server:~$ sudo su - myapp

myapp@server:~$ pwd
/home/myapp

Reimposta la password dell'utente app

Se devi rigenerare la password di un utente app (es. per SSH diretto o SFTP), usa:

bash
$ cipi app reset-password myapp

La nuova password viene mostrata a schermo — salvala subito.

Comandi utili una volta loggato come utente app

bash
# navigate to the active release
myapp@server:~$ cd ~/current

# run artisan directly with the correct PHP version
myapp@server:~$ /usr/bin/php8.5 ~/current/artisan tinker

# inspect the shared .env
myapp@server:~$ cat ~/shared/.env

# tail all logs
myapp@server:~$ tail -f ~/logs/*.log

# check active releases (ll is a built-in alias for ls -al)
myapp@server:~$ ll ~/releases/

Il .bashrc di ogni utente app definisce un comodo alias ll='ls -al' (dalla v4.5.5) per elenchi directory più rapidi via SSH, insieme alle scorciatoie deploy e composer. Le app create prima della 4.5.5 ricevono l'alias ll automaticamente al prossimo cipi self-update via la migrazione 4.5.5.

La restrizione open_basedir dell'utente app limita PHP a /home/myapp. È applicata a livello PHP-FPM, non a livello shell — puoi accedere a qualsiasi file leggibile dal tuo utente shell quando lavori nel terminale.
